# Архитектура EHR-агента

Схема: [architecture.svg](architecture.svg).

Система отвечает на вопрос врача по карте одного пациента. Модель не видит карту целиком. Она вызывает
типизированные инструменты, получает компактные результаты со ссылками на строки карты (id) и завершает работу
вызовом `final_answer` с ответом, цитатами и статусом. Детерминированная обвязка проверяет ответ до того, как
он будет принят.

## Слои

```
           вопрос врача
                │
  agent/  ┌─────▼──────────────────────────────────────────────────────────┐
          │ loop.run_episode: промпт → модель → вызов → результат → …      │
          │ harness: маршрутизация по намерению, проверки ответа, починка  │
          │ llm: GigaChat (functions API) · Qwen/Med-Qwen (MLX, XML/JSON)   │
          └─────┬──────────────────────────────────────────────────────────┘
  tools/        │ 12 инструментов + final_answer; ответы ≤ CHAR_LIMITS, с id строк и next_offset
          ┌─────▼──────────┬──────────────────┬───────────────────────────┐
  knowledge/ каталог анализов  референсы (слои)   лексикон/онтология, сущности
  retrieval/ BM25 + dense e5 + RRF, контекст документа
          └─────┬──────────┴──────────────────┴───────────────────────────┘
  sources/      │ Patient / Record — единая модель для обоих источников
          ┌─────▼──────────────┐   ┌──────────────────────────────────────┐
          │ checkup_xlsx: чекап │   │ inpatient_pdf: история болезни 003/у │
          │ (строка = поле)     │   │ (страницы → блоки и строки LIS,      │
          │ P003:r351           │   │  маскирование ПДн)  K04:p71:b3        │
          └────────────────────┘   └──────────────────────────────────────┘
```

Зависимости направлены строго вниз. `eval/` использует все слои, но ни один слой не зависит от `eval/`.

## 1. Источники (`sources/`)

| Модуль | Что делает |
|---|---|
| `records.py` | `Record` (id, дата, документ, специальность, группа, параметр, значение, число; для PDF ещё бланковая норма, флаг и единицы) и `Patient` (пол, возраст и его происхождение). Определение специальности по заголовку документа. |
| `checkup_xlsx.py` | Выгрузка чекапа: одна строка Excel = одно поле протокола. Id `P003:r351` — номер строки выгрузки. Возраст берётся из `data/assumed_ages.json` (в выгрузке он скрыт анонимизацией). |
| `inpatient_pdf.py` | PDF-история болезни, сшитая из документов разных врачей. Страницы с таблицей LIS дают строки анализов (`K04:p12:l3`), остальные страницы режутся на блоки «Метка: текст» (`K04:p71:b3`). ПДн маскируются до создания записей: токены ФИО пациента в любом регистре и падеже, ФИО персонала, телефоны, адреса, дата рождения и номер карты. Возраст вычисляется на дату госпитализации, сама дата рождения не сохраняется. |

`get_patient(pid)` — единая точка входа. Id на `P` загружаются из xlsx, id на `K` — из PDF.

## 2. Базы знаний (`knowledge/`)

| Модуль | Содержимое | Источник |
|---|---|---|
| `analytes.py` | Каталог ~70 показателей: код, русские, латинские и LIS-синонимы, единицы, ориентировочный интервал, панель. Правила внутренних тождеств (MCHC = HGB/HCT и др.) и пределы физиологической правдоподобности. Правдоподобность проверяется только без лабораторного бланка: бланк задаёт свои единицы. | Собран вручную по открытым справочникам |
| `reference.py` | Политика референсов `layered` (бланк → порог клинических рекомендаций → NHANES по полу и возрасту → ориентировочный каталог) и `indicative` (бланк → каталог). Каждый ответ сообщает, какой слой сработал. | `EHR_REF_POLICY` |
| `nhanes.py` | Прямой метод IFCC/CLSI: здоровые референсные лица NHANES 2017–2018, взвешенные 2.5/97.5 перцентили, упрощённый LAVE, минимум 120 человек на партицию. FT4 пропущен из-за несопоставимости методов. | CDC NHANES XPT → `data/nhanes_ri.json` |
| `lexicon.py` | Синонимы протоколов (ФВ ↔ фракция выброса), онтология для расширения запроса (классы препаратов по ATC с МНН и торговыми названиями, бытовые → клинические термины), состав панелей. | Курирован вручную |
| `dynamics.py` | Reference change value: RCV = 1.96·√2·√(CVa² + CVi²). Изменение меньше RCV считается шумом измерения. Направление хода (рост, снижение, рост затем снижение), нормализация. | CVi по EFLM BV database (округлённо) |
| `critical.py` | Уровни значимости. **Критично:** критические пределы (K⁺, Na⁺, глюкоза, Hb, тромбоциты…), любое повышение тропонина, кратное превышение АЛТ/АСТ/КФК/креатинина, находки текста, требующие действия (новообразование, инфаркт, тромбоз, ФВ < 40 %), без отрицаний и доброкачественных. **Значимо:** прочие отклонения. **Фон:** всё остальное. | Типовые списки критических значений, курировано вручную |
| `entities.py` | Сущности в духе FHIR. `MedicationMention`: препарат по МНН, доза, кратность и фаза (до госпитализации, стационар, во время вмешательства, при выписке), фаза выводится из метки поля. `StudyReport`: вид исследования, дата, заключение. | Правила поверх `lexicon` |

## 3. Поиск (`retrieval/`)

`HybridIndex` объединяет BM25 (стемминг по 5-символьному префиксу и синонимы) и dense-поиск
(multilingual-e5-small, локально, на CPU, с кэшем эмбеддингов) через Reciprocal Rank Fusion (k = 60). Запрос
расширяется онтологией. Результат группируется по документам: найденные строки возвращаются вместе с
заключением своего документа. Офлайн-бенчмарк `eval/retrieval_bench.py` сравнивает варианты по Row@k
(найдена эталонная строка), Ctx@k (строка видна в контексте документа) и Doc@k.

## 4. Инструменты (`tools/`)

| Инструмент | Модуль | Для чего |
|---|---|---|
| `get_overview` | text | Пол, возраст, документы по специальностям, предупреждения о качестве данных |
| `search_notes(query, specialty, top_k)` | text | Гибридный поиск по тексту карты с контекстом документа |
| `get_conclusions(specialty, offset)` | text | Заключения, диагнозы и рекомендации специалистов |
| `get_diagnoses` | text | Компактный список диагнозов (МКБ-10 и текстовые) |
| `get_document(document_id, offset)` | text | Все поля одного документа постранично |
| `get_lab(analyte)` | labs | Значения показателя с интервалом, флагом H/L/N, источником интервала и отметкой качества |
| `list_abnormal_labs(panel, offset)` | labs | Все показатели вне интервала, с фильтром по панели |
| `calculate(formula, …)` | labs | ИМТ, non-HDL, HOMA-IR, де Ритис, СКФ CKD-EPI, FIB-4 |
| `check_consistency` | quality | Противоречия роста и веса, нарушения тождеств анализов, неправдоподобные значения |
| `get_trend(analyte)` | summary | Ряд значений по датам, первое, пиковое и последнее, изменение в % против RCV, нормализация |
| `build_dossier` | summary | Полное досье для сводки: отклонения с динамикой, исследования, диагнозы, препараты по фазам, рекомендации, качество данных, уровни значимости и `must_mention` |
| `get_medications(drug, drug_class, phase, offset)` | clinical | Назначения из всех документов, нормализованные по МНН, с фазой |
| `get_studies(kind)` | clinical | Инструментальные исследования: дата, заключение, ключевые значения |
| `final_answer(answer, citations, status)` | — | Завершение: ответ, id строк, статус `answered`, `not_found` или `uncertain` |

Общие принципы (`tools/base.py`):

- **Аргументы проверяются по схеме.** Ошибка возвращается модели как исправимое сообщение.
- **Результат ограничен по длине** (`CHAR_LIMITS`). Длинные списки режутся с `next_offset`, их не обрывают на середине JSON.
- **Пустой результат явный** (`found: false`, `checked_records`). Модели предлагается сменить запрос или ответить `not_found`.
- **Каждый факт несёт id строки карты.** На этот id модель ссылается в `citations`.

Наборы (`TOOLSETS`): `full` — 12 (без `build_dossier`), `report` — 12 + `build_dossier`, `compact` — без `get_medications` и `get_studies`, `code` — только
`run_python` над DataFrame карты, `none` — без инструментов.

## 5. Агент (`agent/`)

**Ход эпизода** (`loop.run_episode`):

1. Выбранная система (`systems.py`) определяет набор инструментов, наличие карты в промпте и включённые функции обвязки.
2. Если система это предусматривает, `harness.route_intent` определяет намерение вопроса (анализ, отклонения, согласованность, диагнозы, препараты, исследования, свободный текст). Затем модели показываются только относящиеся к нему инструменты (`tools_routed`) или нужный инструмент вызывается заранее (`tools_prefetch`).
3. В цикле модель вызывает инструменты до исчерпания бюджета (по умолчанию 4). Повторные вызовы обслуживаются из кэша, невалидные возвращают ошибку.
4. Если модель ответила текстом, срабатывает починка формата: принудительный вызов `final_answer`. Если и это не удалось, ответ извлекается из текста.
5. Ответ проверяется (`harness.check_answer`): цитируемые id должны существовать, числа — встречаться в карте или выводе инструментов, а ответ «нет данных» обвязка перепроверяет широким поиском. Каждая проверка срабатывает не больше одного раза за эпизод.
6. Если ответ на сообщение обвязки оказался бессодержательным («вот id…»), сохраняется первый содержательный ответ (`keep_substantive`).

**Системы** (`systems.py`):

| Система | Инструменты | Карта в промпте | Проверки и починка | Роль в эксперименте |
|---|---|---|---|---|
| `tools` | full | — | да | основная система |
| `tools_routed` | по намерению | — | да | меньше выбора для слабых моделей |
| `tools_prefetch` | full + упреждающий вызов | — | да | экономия одного вызова |
| `tools_compact` | compact | — | да | влияние размера набора |
| `tools_plain` | full | — | нет | абляция обвязки |
| `code` | run_python | — | нет | базовая линия: интерпретатор кода |
| `record` | — | да | нет | базовая линия: длинный контекст |
| `report` | report, досье заранее | — | да + полнота и вердикты | сводка карты: единый отчёт |
| `report_nocheck` | report, досье заранее | — | да, без полноты и вердиктов | абляция проверок отчёта |
| `record_chunked` | — | по фрагментам (map-reduce) | нет | базовая линия: длинная карта без инструментов |
| `record+tools` | full | да | да | помогают ли инструменты при равном доступе к данным |

**Отчётные системы** (`report`, `tools/summary.py`). Сводка проваливается в основном из-за пропусков:
модель сама выбирает, какие инструменты вызвать, и пропускает целые разделы. Поэтому сбор делает код:
1. `build_dossier` вызывается обвязкой заранее и попадает в промпт.
2. Модель пишет отчёт вызовом `final_answer` с полем на каждый раздел: ключевые выводы, анализы, динамика,
   исследования, диагнозы, терапия, качество данных, рекомендации, сознательно не включённое. Каждый пункт —
   «факт — значение — вердикт — динамика — [id]».
3. `render_report` собирает разделы в один Markdown-документ, одинаковый для всех моделей.
4. Обвязка проверяет отчёт по досье (`harness.check_report`):
   - **полнота:** каждый пункт `must_mention` назван, процитирован его id или пункт перечислен в «не включено»;
   - **вердикты:** анализ с флагом H/L не назван «нормой», направление динамики не противоречит ряду.
   Каждая проверка срабатывает один раз; модель получает исправимую ошибку с перечнем пропусков.

**Map-reduce базовая линия** (`chunked.py`). Целая PDF-карта (до ~200 тыс. токенов) не помещается в контекст,
поэтому `record` на длинных историях болезни неприменим. `record_chunked` режет сериализованную карту на фрагменты
по ~60 тыс. символов (`EHR_CHUNK_CHARS`), не разрывая записи: таблица чекапа — 2–3 фрагмента, PDF — 5–9.
На каждом фрагменте модель без инструментов выписывает относящиеся к вопросу строки. Обвязка подставляет в выписку
исходные строки карты: по названным id, иначе по совпадению слов процитированного фрагмента (не меньше 60 %).
Это нужно, потому что слабая модель часто возвращает голое число без id. Reduce-шаг — обычный цикл без
инструментов над выписками. Стоимость растёт с длиной карты, а не со сложностью вопроса: один вызов модели на
фрагмент плюс один на ответ.

**Бэкенды** (`llm.py`) имеют единый интерфейс `chat(messages, tools, force_final) → Reply`:

- **GigaChat.** REST `functions`. При принудительном вызове передаётся только спецификация `final_answer`: с полным списком функций API отвечает 422.
- **Qwen3.5-4B и Med-Qwen** работают через MLX. Вызовы разбираются из XML- и JSON-разметки. KV-кэш префикса переиспользуется между шагами. У Med-Qwen есть блок `<think>` и явный стоп `<|im_end|>`.

## 6. Оценка (`eval/`)

| Модуль | Что делает |
|---|---|
| `gold.py` | Шаблоны вопросов и эталонов по категориям: lookup, abnormal, integrate, not_found, quality, icd, anthropo, freetext, summary. Уровни строгости формулировок L1–L3, PDF-вопросы, проверочные наборы. |
| `benchmark.py` | Вычисляет эталоны по данным (тип эталона: numeric, set, codes, facts, checklist, conflict, not_found, uncertain) и `support_rows` — строки карты, подтверждающие ответ. Результат: `data/questions.jsonl`. |
| `run.py` | Сетка прогонов (модели × системы × бюджеты × повторы) → `runs/*.jsonl`. Прогон возобновляемый. Эпизоды с ошибкой бэкенда не сохраняются. |
| `score.py` | Автоматическая оценка: верность по типу эталона, валидность цитат, покрытие опорных строк, числа, отсутствующие в карте. |
| `score.py` (сводки) | Для всех систем на сводках дополнительно считается `critical_recall` — доля пунктов `must_mention`, покрытых ответом (то же правило, что в проверке полноты). |
| `analyze.py` | Точность с бутстреп-ДИ по моделям, системам, категориям и источникам. Эталон берётся по политике референсов эпизода, `context_overflow` считается N/A. |
| `behavior.py` | Профиль вызовов, локус ошибки (поиск или использование найденного), калибровка статусов, обоснованность, задержка и токены, примеры траекторий. |
| `retrieval_bench.py` | Офлайн-бенчмарк поиска без LLM. |
| `pii_audit.py` | Поиск остатков ПДн в замаскированных PDF-записях. Печатает только счётчики. |
| `review.py` | План тестов одной локальной HTML-страницей (`data/test_plan.html`): схема, наборы, категории, системы, все вопросы с эталонами и опорными строками, unit-тесты. |
| `ri_compare.py` | Сравнение политик референсов. |
| `labels.py` | Подписи систем, порядок моделей, цвета графиков. Здесь же соответствие названий исследовательских итераций v1–v4 из `runs/` финальным системам (подробнее в `archive/exploratory_code/README.md`). |
